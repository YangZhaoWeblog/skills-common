# Review Gate

这是新写、重写、大改、高影响或带图个人文章的**强制交付闸门**。独立 reviewer 只负责发现 writer 看不见的问题，不改原文。

## 硬性规则

- 最终成品在独立 Review `pass` 前不得交付。新写或大改时，不得创建、覆盖或修改最终目标路径；候选稿只能写入明确标记的 draft/temp 路径，`pass` 后才能提升到目标路径。
- 独立 reviewer 必须来自独立调用、子代理或隔离评审上下文。writer 自己重新读一遍、自己套 checklist，或在同一上下文中临时扮演 reviewer，都不算。
- 如果环境具备独立子代理或隔离评审能力，必须实际调用；未尝试已有能力，不得声称“没有独立 reviewer”。没有独立 reviewer 能力，或缺少实际调用/隔离证据时，Review Gate 状态为 `blocked`。必须停下并向用户说明“独立 Review 未完成”，不能用自审替代，也不能报告完成。
- 触发 Review Gate 时生成 `gate_id`，标识本次修改任务并关联目标身份。它不永久绑定文章；同一未完成任务换会话、改名或移动时，继续跟踪原有审查问题。
- Review 结论必须在交付记录中留下 `gate_id`、规范化目标路径或文章身份、候选版本的 SHA-256、系统生成的 reviewer 调用 ID、原始返回结果或隔离会话 ID/审计记录、Review 包、轮次、结论和剩余风险。reviewer 必须实际收到并审查该 SHA-256 对应的版本；手写 reviewer 名称、手写“已通过”或未定义的“隔离证据”不算证据。
- 本次 Gate 关闭前，Review 之后的任何候选内容改动都会使原结论失效；最终版本必须重新交给独立 reviewer 确认，并核对版本路径和 SHA-256。提升到最终目标路径后，最终文件 SHA-256 必须与 reviewer 审查的候选版本一致；路径身份或哈希不一致时为 `blocked`。通过、交付并验证一致后关闭 Gate。
- 本次任务内轮次递增，不设最多两轮。任务通过并交付后关闭本次 Gate；后续新任务按实际影响重新判断是否触发。未解决的问题不能通过拆分任务、改名或新建标识清除。
- 记录丢失时先查找可核验的旧记录；无法恢复则建立注明来源缺失的恢复记录，对当前候选重新独立审查，不推定历史通过或伪造轮次。标识丢失本身不造成永久阻塞。

## 触发

- 新写、重写、大改、带图或高影响文章。
- 用户明确要求审查。
- 自审发现标题链、事实或视觉结构不稳。

已完成任务后的错别字、局部润色和用户明确要求的快速改动，按当前影响判断，可豁免独立 Review。同一未完成任务的累计实质改动不能拆成小改规避；当前候选接受审查后再变化，仍按版本失效规则处理。

## 最小 Review 包

- 文章目标、读者、使用情境与当前阶段，包括共同背景、可用讲解及独立阅读要求。
- 当前成品、必要事实来源和来源优先级。
- 已确认的术语、事实、范围和风格。
- 概念或解释文要建立的定义与关系，或决策文的问题、判断依据、选择与调整条件；不要求默认选择先行。
- 用户认可的参考样本；没有则明确标无。
- 文章路径、图片路径和对应检查表。

复杂决策文可附内部判断账本，但不附 writer 的中间推理或预期答案。

reviewer 只读 Review 包、目标文章、必要事实源和 checklist；带图时附视觉检查表和图片路径；不读完整聊天、writer 中间推理或预期答案。

Review 包不能包含 writer 的预期结论、怀疑的问题、修复方案或要求 reviewer 证明的答案；否则 reviewer 只是在确认 writer 的判断，不是独立审查。

## Review 记录与状态

交付记录至少保留以下字段；缺少任一字段时，状态为 `blocked`：

```text
gate_id: 本次修改任务的 Gate 标识
article_id: 稳定文章身份
target_realpath: 规范化目标真实路径或文件身份
candidate_sha256: reviewer 实际收到的候选版本哈希
review_package_sha256: Review 包哈希
reviewer_call_id: 系统生成的独立调用 ID
reviewer_result: 原始返回结果或隔离审计记录
round: 本次任务已记录的实际调用轮次，递增；恢复记录不虚构旧轮次
state: triggered | reviewing | needs_fix | pass | invalidated | blocked
final_sha256: pass 后最终目标文件哈希
```

状态只能按以下路径推进：

`triggered → reviewing → pass`，或 `triggered → reviewing → needs_fix → reviewing`，修复与复审可重复，直到 `pass` 或出现真实阻塞。

本次任务交付前，候选版本改动会使已有 `pass` 变为 `invalidated`，需审查新版本。第二轮未通过时继续按问题修复，不按次数变为 `blocked`。Review 包、原始审查结果与最终文件必须对应同一候选内容；各自记录实际哈希，不要求不同文件的哈希相等。任务通过并交付后归档记录，后续任务不继承耗尽额度。

## Review 重点

- 标题和视觉中心是否呈现本节的定义、关系、判断或行动任务；话题与使用场景切换是否清楚，不机械要求结论先行。
- 每个关键判断是否只有一个主载体；其他位置的条件、例外、证据或动作是否为当前理解或使用所必需，并通过删除检验。
- 按 [current-content-integrity.md](../../td-logic-writer/references/current-content-integrity.md) 的统一目标、最小充分解释与删除检验审查：必要关系是否够，读者懂后是否停，删句有何具体损失；不按字数或句数判断，不机械要求补例子、反例或总结。
- 规则依据是否分清约束、价值选择、判断依据与试行办法；逻辑漏洞应指出并提出修正，不暗改用户事实、价值选择或数值。
- 图、表、文字是否分工；每张表是否真的服务横向比较，而非包装规则、步骤或段落；事实与个人策略是否清楚分开。

## 输出

| 结论 | 处理 |
| --- | --- |
| pass | 可交付 |
| minor | writer 修复后由独立 reviewer 复核最终版本 |
| structural | 回到骨架，修复后重新 Review |
| factual | 停止并查证，修复后重新 Review |
| visual | 先改图文分工，修复后重新 Review |
| blocked | 不交付，向用户报告阻塞 |

报告只写：目标路径、候选版本标识或内容哈希、reviewer 标识、实际调用结果或隔离上下文证据、结论、问题位置、问题为何影响阅读或准确性、必须修复项、剩余风险和复审轮次。

## 暂停与恢复

只有缺少关键事实或授权、独立审查能力不可用、版本证据不一致，或连续两次修复后同一关键问题仍无实质进展时，暂停并记录具体阻塞及解除条件。需要用户信息时只问关键问题；可自行查证或换修复方法时先处理。单纯到达某一轮次不构成阻塞。

阻塞解除后沿用本次任务记录，`blocked → needs_fix/reviewing`，修复并重新独立审查。恢复不等于通过；最终候选获得 `pass` 且验证一致后才能交付。
