# 当前成品真源与正文完整性

## 核心原则

**当前成品服务当前任务和已确认范围。** 不为说明改过什么而补回用户删除的对象或编辑旁白。当前判断所需的真实对比、历史证据，以及用户要求的变更文档或记录应保留，明确事实来源和时间范围；不得借此恢复用户明确要求排除的内容。

## 按使用情境选择解释量

先确认读者已有背景、可用讲解和再次使用的时间，再决定正文承担多少解释。

| 使用情境 | 正文的责任 |
| --- | --- |
| 会议技术材料：共同背景、口头讲解或录屏、短迭代 | 保留本次变更、依据、待决定项和当前实施必要契约。共享背景可简写或引用，不默认扩成长期档案；接口语义与边界不能只靠口述。 |
| 个人决策：未来可能忘记上下文的自己 | 精练地保留问题、理由、判断规则和调整条件，使未来的自己能恢复理解。 |
| 博文：陌生读者独立阅读 | 补齐必要背景、概念和关键关系；帮助读者独立理解的解释不是噪声。 |

**审查标准是：在约定的阅读情境下，读者是否仍需自行补出关键关系。** 扫描路径帮助定位，连续解释帮助理解，两者不能相互替代。删除或移走内容前，确认正文与读者实际可用的引用仍能承接理解。

## 规则依据

分清约束、价值选择、判断依据和试行办法：约束限定可行范围，价值选择说明优先保护什么，判断依据支持具体取舍，试行办法在不确定时提供可调整的做法。它们可以共同支持规则，不必从一个“本质”强推；规则解释应说明解决什么问题，以及按什么反馈调整。这些层次用于写作和审查，正文可自然表达，不必显式贴标签。

## 完整正反短例

以下是虚构的写法示例，不是可直接套用的规则。

### 会议技术材料

**反例：** 本次改用异步回调，提高效率，让处理更科学。具体行为会上说明。

**正例：** 本次将导出请求改为异步，依据是联调中大文件处理超过网关超时。请求返回任务 ID，完成后回调结果；调用方按任务 ID 去重，失败后可查询任务状态。会上需决定回调失败是否自动重试，由接口双方确认后补入本次契约。原导出流程沿用现有说明。

正例保留变更依据、实施必要契约和待决定项；反例只有口号，实施者仍需猜测行为。

### 个人决策规则

**反例：** 时间管理的本质是效率，因此每天只安排三件事，坚持执行就能更科学地管理时间。

**正例：** 最近每天排满任务，临时请求一来，原定工作就做不完。工作日只有两小时可自主安排，我更希望核心项目能持续推进。先按预计耗时和延期损失排任务，留半小时处理临时请求，试行两周。若仍频繁延期，就减少承诺；若缓冲持续闲置，再缩短预留时间。

正例中，两小时是容量约束，核心项目优先是价值选择，耗时与延期损失是排序依据，预留半小时、试行两周是试行办法，延期与缓冲使用情况是调整依据。正文自然交代问题和理由，层次由点评辨认；反例把试行办法写成由“本质”推出的必然结论。“提高效率、更科学”不能替代具体理由。

### 面向陌生读者的博文

**反例：** 重试要保证幂等。使用幂等键即可。

**正例：** 请求超时时，调用方不知道服务端是否已经处理成功，直接重试可能重复扣款。幂等键为同一次扣款提供稳定标识；服务端把该标识与处理结果一起保存，再次收到同一标识时返回原结果。因此重试要复用原键，生成新键会被视为另一笔请求。

正例补齐超时、重复执行和幂等键之间的关系；这些解释是独立理解所需的正文。

## 正向 Schema

Schema 是检查遗漏与关系的路径，不是固定目录。只在确有依赖时使用因果推进；案例用于弥补具体理解缺口，不要求每节举例或设置贯穿案例。并列事项可用 bullet，关键关系用必要的连接句说明。

按段落职责检查信息贡献，不把全部句子套成动作链：

| 职责 | 正向 Schema | 示例 |
| --- | --- | --- |
| 定义 | 对象 → 含义或边界 | 任务是具有明确完成条件的工作单元。 |
| 证据 | 来源/条件 → 观察结果 → 支持范围 | 本次样本中 A 的失败率更低；结论限于该测试环境。 |
| 判断/行动 | 对象 → 判断依据 → 选择或动作 | 任务太多时，先确定优先级，再安排执行。 |
| 必要对比/变更 | 可核查的差异 → 当前意义 | 本次接口将同步返回改为异步通知，调用方需处理回调。 |

写入前检查：这段是否帮助读者理解对象、核查证据或形成判断？定义与证据无需各自附带动作；仅因没有动作而删除，会破坏正文完整性。

## 负向 Schema

| 失败模式 | 典型形态 | 处理方式 |
| --- | --- | --- |
| **历史残留** | “四象限只是处理方式；本页最终……”但本节尚未讨论四象限 | 删除历史对象，直接写当前主张 |
| **编辑过程泄漏** | “原来……后来改成……现在……”，仅描述写稿过程 | 删除无关旁白；真实必要对比或用户要求的变更记录保留 |
| **替代说明残留** | “不是 A，而是 B”，但 A 不是读者当前需要区分的对象 | 删除 A，只写 B 的当前判断 |
| **范围污染** | 为了说明某概念不重要，先把它引入标题或开头 | 不引入该概念；把边界放到真正需要它的章节 |
| **旧标题回声** | 正文无关地继续解释已删章节名、旧术语或旧分类 | 删除回声；不能仅因改过标题就删除仍必要的定义与事实 |
| **删改旁白** | “这里不再讨论……”“前面删除了……” | 从正文删除；必要的变更记录留在工作记录或 Git diff |

## 删除测试

每次删掉或替换一个概念后，检查三件事：

1. 删除该概念后，是否损失必要定义、证据或对比？只留下无关编辑痕迹时不补回。
2. 读者只看当前标题和正文，是否会误以为该概念仍属于本文主线？会就继续删。
3. 本段是否仍服务当前任务，且没有把历史事实误写为当前状态？不要求每段同时具有判断和动作。

**不要为了证明删除发生过，而在成品里留下删除痕迹。**
