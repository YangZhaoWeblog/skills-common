# 技术文档写作

目标是组间同步：让读者快速对齐目标、变更、边界、证据和责任。

## 路由

| 任务 | 读取 |
| --- | --- |
| 所有正式文档 | [information-design.md](references/information-design.md) |
| 系统、协议、接口、数据或流程改造 | [change-design.md](references/change-design.md) |
| 根因、兼容性、性能、可行性验证或测试报告 | [verification-research.md](references/verification-research.md) |
| 交付审查 | [review-checklist.md](references/review-checklist.md)；必要时 [review-gate.md](references/review-gate.md) |

局部改字只读当前文件和相关规则。正式写作、重写或大改必须读取当前文件、权威事实源和对应 reference。

不用于个人判断框架、概念边界文或 Obsidian 项目认知文章；转给 **td-logic-writing-flow**。没有团队同步对象、技术真源、验证证据或变更契约的个人运行规则，也转给 **td-logic-writing-flow → td-logic-writer 的个人系统/决策文档模式**。

## 通用规则

1. **按断言选择真源**：目标决策以用户最后确认的需求或成品为准；现状事实以当前代码、协议和数据结构为准；当前文件是待核对的编辑基线；旧稿和历史讨论只供追溯。写入前重读目标文件。
2. **先分清变化**：区分既有事实、本次新增、修改、删除和明确不变。既有取舍不因重新发现自动升级为本次问题。
3. **一个章节一个中心**：先确定读者第一眼看什么，再补必要证据。图写关系和流程，表写共同维度上的稳定比较和变更，文字写判断、理由和边界；不要用表格包装规则、步骤或长解释。
4. **样式服从扫描**：正文中的类型、方法、字段、状态、路径、关键结论、风险边界、改造口径和待确认项使用 **加粗**，形成第二阅读路径；不用行内代码样式。仅可执行片段使用代码块。
5. **无损压缩**：正式文档只保留当前评审所需内容；问题树、讨论过程和长证据留在旁路记录。调研的环境、方法、结果和限制属于证据，不能因压缩删除。
6. **纠正全局传播**：用户确认的术语、事实、范围和风格必须同步到全文；用户删除或否定的内容是负向样本。
7. **当前成品只写当前契约**：旧方案、被删除字段、历史讨论和编辑过程不进入正文；除非旧内容本身是当前兼容性、迁移或风险证据，否则不得用“以前/现在”“不是 A 而是 B”或“这里不再讨论”保留删除痕迹。
8. **默认最小章节数**：优先 3–5 个主章节；无团队模板或既有格式约束时，中文正式文档主章节默认使用 `一、二、三、四` 编号；新增章节必须比现有表、图或短段更能降低组间不确定性。
9. **先确定文档推进关系**：正式文档必须明确是诊断异常、比较方案、验证可行性、描述变更，还是指导操作；每节都要减少一个不确定性、闭合一个契约或确定一个动作。只增加同层背景的章节应合并或移到旁路。

## 类型骨架

| 类型 | 默认骨架 |
| --- | --- |
| 迭代型变更设计 | 共享状态或关系图（有则前置） → 背景 → 受影响的数据结构/库表 → 受影响的接口/方法 → 受影响的核心流程 |
| 问题诊断型调研 | 背景与异常 → 假设 → 验证矩阵 → 结论 → 建议 |
| 覆盖型兼容性调研 | 背景与结果总览矩阵 → 分项证据 → 改造边界 |
| 架构/选型 | 背景与约束 → 对比 → 决策 → 落地与风险 |
| 性能/可行性调研 | 问题与阈值 → 指标/样本 → 结果 → 结论与边界 |
| 测试报告 | 范围与环境 → 方法 → 结果 → 结论 |
| 操作手册 | 前提 → 步骤 → 验证 → 故障处理 |

没有共同状态或关系时，用结果总览、对比表或结构定义作为全文视觉中心。没有真实选项时，不制造选型章节。

## 调研与设计交接

关键证据未建立时，先交付验证调研；结论确认后再进入变更账本和独立设计文档。用户必须合并为一篇时，先写证据摘要，再写只基于已证实结论的变更设计。

## 工作流

1. **定型**：确定类型、读者、组间同步对象、权威来源和责任边界。
2. **审计**：建立内部变更账本或证据清单；一次只讨论一个会改变方案的决策。提问前说明背景、阅读位置和影响。
3. **骨架**：章节只能来自变更账本或证据清单；为每节确定“问题 → 视觉中心 → 必要证据”。新写、重写、大改默认先给标题链。
4. **落笔**：按对应 playbook 写入。只画变化流程；状态图标明允许动作；精确图优先可编辑源格式。
5. **交付**：逐项对照真源和内部账本；检查 Markdown、图和图片在目标平台可用；按 checklist 自审。非平凡文档使用独立 reviewer。

## 复盘

用最终认可成品和用户删改记录，输出“纠正 → 失败模式 → 最终模式 → 是否通用 → 反哺位置”。只把跨项目规律写回公共 Skill。
