# 信息设计

## 扫描路径

读者应按“标题 → 视觉中心 → 必要文字”完成一节。标题呈现结构，加粗呈现关键判断；视觉中心给结构或结论，正文保留必要定义、证据、理由、例外和后果。

定义/决策型标题用准确精练的对象词组，同级保持相称层次，按对象关系与阅读依赖排序；操作手册可用动作标题。标题不必复述结论，不设字数硬限；分项定义与证据可以并列查阅。

精练不能删除影响正确理解的限定；操作标题中的执行前提或放行条件必须明确，例如“验证通过后开放流量”，不能缩成“验证并开放流量”。

| 语境 | 正向 Schema | 反向 Schema |
| --- | --- | --- |
| 设计或选型 | 数据模型 → 接口契约 → 核心流程；正文加粗关键变更与判断 | 先想清楚 → 再改一改：对象不明；或把全部变更细节塞进标题 |
| 操作手册 | 检查备份 → 执行迁移 → 验证结果 | 将动作标题强加给所有定义与决策章节 |

示例仅说明标题选型，不要求所有文档使用同一章节链。

| 章节任务 | 首选中心 |
| --- | --- |
| 生命周期、操作边界 | 状态机，节点旁标允许动作 |
| 数据模型、协议结构 | 结构定义或 ER 图，加变更表 |
| 接口、方法、事件改动 | 变更矩阵 |
| 多角色、异步闭环 | 时序图 |
| 方案比较 | 对比表和明确结论 |
| 兼容性、测试覆盖 | 结果总览矩阵 |

没有稳定比较维度时不用表；没有空间关系时不用图。图或表已表达的信息，不在正文逐行复述。

表格只服务可并列的信息项、共同列和横向扫读，或评审约定的固定变更矩阵；接口、字段、变更、测试结果通常满足这个条件。规则和门槛用短段或清单，时间顺序用步骤或时序图，长解释不用切成网格。

## 表格

- 表名和列名必须直接表达比较维度，读者不读正文也能理解表在回答什么。
- 变更表必须显式覆盖账本中实际存在的新增、修改、重命名、删除和语义调整；不造“无变更”行。
- 接口表优先使用：**接口｜变更类型｜请求变更｜响应变更｜备注**。
- 数据表优先使用：**表/结构｜说明｜改造**。
- 备注只放压缩后的业务语义、理由或跨组动作，不承担本应出现在列名中的信息。
- 单元格应是可扫读的事实或短判断；若它需要完整段落，拆回正文、清单或图。

## 图与分隔

- 状态图、时序图、ER 图优先 Mermaid、DBML 或其他可维护源格式。
- 状态图区分业务状态和技术处理中状态；后者不应伪装成业务节点。
- 时序图只保留本次变化的参与者、门禁、调用、事件和落库。
- 分隔线用于切换阅读任务，例如“结论 → 证据 → 实施边界”；不作为机械装饰。

## 文字

- 保留定义、证据、最终结论、变更、必要理由和边界；删除无关讨论过程、重复解释和礼貌过渡。真实必要对比和用户要求的变更记录不属于编辑旁白。
- 名称性信息、关键结论、风险边界、改造口径和待确认项使用 **加粗**，形成第二阅读路径；不用行内代码样式。
- 代码仅展示结构、签名或决策点；完整实现留在代码库。
