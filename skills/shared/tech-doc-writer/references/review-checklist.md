# 技术文档检查表

## 通用

- 只扫标题和视觉中心，能否说清目标、边界和结论？
- 是否以当前文件、当前代码和用户最新确认作为真源？
- 用户纠正的术语、事实、范围和样式是否传播到全文？
- 每节是否只有一个主要视觉中心？
- 骨架阶段选定的结构定义、表、图或短段是否落实，读者能否据此回答该节问题，而不只是看到同名标题？
- 已有材料中的关键图、结构或证据是否按评审需要保留、裁剪或引用；精简后是否丢失字段归属、参与者、时序或结果边界？
- 图、表、正文是否各自承担不同信息？
- 每张表是否有可并列的信息项、共同维度和横向扫读价值，或属于约定的固定变更矩阵；是否误把规则、步骤或长解释做成表格？
- 是否删除了讨论过程、重复解释和无关旧问题？
- 正文是否服务当前评审契约，删除无关编辑旁白，同时保留必要的真实对比、历史证据、删除项及用户要求的变更记录？
- 加粗是否覆盖名称性信息、关键结论、风险边界、改造口径和待确认项，形成第二阅读路径，且没有行内代码样式？
- 阅读组织方式是否服务诊断、比较、验证、变更、操作或并列查阅；是否保留必要定义与分项证据，避免强制逐节因果或每句动作？
- 标题是否对象明确、层级一致、逻辑排序，采用适合文档类型的表达；标题呈现结构、加粗呈现判断，而非强制标题复述结论？
- 是否把个人运行规则误写成正式团队技术文档，或反过来把正式变更写成个人观点？
- 若作为公共 Skill 范例，正文、图源、图片及附件是否仍暴露真实项目的部署方式、数据分发、权限判定、加密机制或特有规则；案例是否真正独立虚构，而非原系统的逐项改名？

## 变更设计

- 如存在共同状态或关系模型，是否在前置位置？
- 数据和接口均受影响时，数据结构是否先于接口？
- 新增、修改、重命名、删除、语义调整是否逐项闭合？
- 新增结构和事件载荷是否定义，复用结构是否避免重复？
- 接口表是否覆盖实际受影响的请求、响应、删除项和共享返回字段？
- 时序图是否只画变化流程和关键门禁？
- 本次涉及的跨角色调用和异步回流，能否辨认调用方、受理回执、成功事件和落库结果；使用局部判断图时，是否仍有足够表达交代这些关系？
- 如存在跨组边界，受影响方是否能看出自己的动作或待确认项？

## 验证调研

- 开头是否有问题、口径和结论摘要？
- 是否有结果总览矩阵？
- 环境、方法、数据、限制是否足以支撑结论？
- 实测、引用和推断是否区分？
- 未测和失败场景是否明确？
- 是否一眼看出改什么、不改什么、为什么？
