# 验证型技术调研

目标是用可核查证据回答技术不确定性；不把探索过程当正文。

## 范围门禁

- 先判断产物是调研报告还是后续实施方案；已有证据只写报告，不虚构测试计划、验收、上线或完整改造设计。
- 新章节必须服务一个已知假设、验证维度或结论边界。
- 环境、命令和原始输出只保留复现结论所需部分，其余放附件。
- 优先 3–5 个主章节；结果总览可同时承载风险判断、改动判断和无需改动项时，不再拆章。

## 先选路径

| 路径 | 核心问题 | 全文中心 |
| --- | --- | --- |
| 问题诊断型 | 异常为何发生，方案是否有效 | 假设或结果矩阵 |
| 覆盖兼容型 | 哪些维度通过，需要哪些改动 | 验证维度 × 结论 × 改动 × 证据位置 |
| 性能/可行性 | 是否达到阈值或具备可行性 | 指标/样本/阈值矩阵 |

## 共同要求

- 开头写问题、口径和结论摘要。
- 每项结论标明实测、文档依据或推断；推断不能伪装成实测。
- 实测记录环境、版本、配置、方法、结果和限制；静态审计记录来源版本和检查方法；推断记录依据和适用边界。
- 失败结果、环境限制和未验证项属于结论边界，不能删除。
- 正文保留支撑结论的最小证据；原始日志、完整命令和冗长过程放附件或旁路记录。

## 问题诊断型骨架

1. 异常与范围。
2. 根因假设。
3. 验证矩阵或关键实验。
4. 结论。
5. 推荐方案与剩余边界。

## 覆盖兼容型骨架

1. 背景与总览矩阵。
2. 分项验证：每节先给结论，再给必要证据。
3. 所需改动、无需改动项和限制。

性能/可行性调研用“指标｜样本｜阈值｜结果｜结论”矩阵。

总览矩阵优先使用：**验证维度｜结论｜是否改动｜关键证据**。改动可以为零、一项或多项。分项表是证据，不能取代总览。

## 测试报告

测试报告使用“范围与环境 → 结果矩阵 → 失败/限制 → 结论”。结果矩阵写场景、断言、实际结果和证据；不要伪装成根因调研或实施方案。

## 交付检查

- 测试是否真正覆盖声称的范围？
- 结论是否能由表、数据或引用直接支持？
- 环境差异和未测场景是否明确？
- 推荐方案是否只解决已证实的问题？
- 读者能否一眼看出“改什么、不改什么、为什么”？
